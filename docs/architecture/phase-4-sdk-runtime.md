# SDK runtime (bytecode architecture)

Contributor reference for the bytecode runtime in `packages/ota_client` (added in Phase 4; the
file name is kept because source comments link to it). Status: experimental alpha, Android arm64
only. Unit-tested on Linux and tested end to end on one Android 13 phone. Follows the
[runtime contract](runtime-contract.md) and the [backend protocol](phase-4-backend-protocol.md).

Developer guide: [Flutter integration](../flutter-integration.md).

mock/AOT paths are unchanged.

## 2. Start-up path (no network)

```text
initialize()
 ├─ parse FLUTTER_OTA_CONFIG            missing/invalid -> DISABLED (log), never throws
 ├─ native startupInfo                  filesDir, versionName+versionCode
 ├─ PatchStore.open(release_id)         <filesDir>/flutter_ota/, leftovers removed, journal resumed
 ├─ lastExit (only if a session marker exists) -> attribute the previous session
 ├─ (only if a patch exists) libappSha256 (native, cached by APK paths + lastUpdateTime)
 ├─ activatePending                     pending.otp -> active.otp (journaled, atomic renames)
 ├─ verifyStored                        full verifyPatch again; on failure restore previous
 ├─ attempt marker, loader(module), parse contract-3 entry, register features
 └─ STARTUP timings log + FlutterOta.lastStartupTimings
first frame (addPostFrameCallback) + stable period (10 s)
 ├─ confirm (PROBATIONARY -> ACTIVE, session marker)
 └─ background update check
```

Timings: `total`, `native`, `libappHash`, `verification`, `moduleLoad`.

## 3. Decision: the module loader (`dynamic_modules`)

**Fact.** `dart:_internal.loadDynamicModule` may only be imported by a package named
`dynamic_modules` or `dart_internal` (checked in the pinned Dart SDK,
`pkg/kernel/lib/target/targets.dart`, `allowPlatformPrivateLibraryAccess`).

**Decision.** The SDK does **not** depend on `dynamic_modules` and does not embed the call:

- the package `flutter_ota_system` cannot import `dart:_internal` under its own name;
- a path dependency cannot be published to pub.dev, and a hosted `dynamic_modules` package would
  have to be published and approved first;
- apps built with a stock Flutter SDK would also break.

Instead, the SDK takes the loader as a function: `typedef FlutterOtaModuleLoader =
Future<Object?> Function(Uint8List)`. The toolchain bundle (4B) ships the `dynamic_modules`
package, and the CLI adds it to the app and generates the code below.

**Developer `main.dart` stays exactly** `WidgetsFlutterBinding.ensureInitialized(); await
FlutterOta.initialize(); runApp(...)`. Dart has no code that runs on import, so the loader
cannot be registered by `flutter_ota_features.g.dart` alone. The simplest robust option is a
**generated build target**:

### What the generator (4D/4F) must emit

1. `pubspec.yaml` of the app: a dependency `dynamic_modules` (path into the toolchain bundle).
   The `dynamic_modules` wrapper is the Phase 1-3 one:
   `Future<Object?> loadModuleFromBytes(Uint8List bytes) => internal.loadDynamicModule(bytes: bytes);`
2. `lib/flutter_ota_main.g.dart`, exactly (if the app's `main` takes `List<String> args`, pass
   them through):

   ```dart
   // GENERATED by flutter_ota. Do not edit.
   import 'dart:typed_data';

   import 'package:dynamic_modules/dynamic_modules.dart' as dm;
   import 'package:flutter_ota_system/flutter_ota_system.dart';

   import 'main.dart' as app;

   /// Found by name in the verifier process: keep the pragma.
   @pragma('vm:entry-point')
   Future<Object?> flutterOtaLoadModule(Uint8List bytes) => dm.loadModuleFromBytes(bytes);

   void main() {
     FlutterOta.registerModuleLoader(flutterOtaLoadModule);
     app.main();
   }
   ```

3. `flutter_ota release android` (and the patch build that computes the dynamic interface) must
   build with `-t lib/flutter_ota_main.g.dart`.

If an app is built without this target, `initialize()` logs
`DISABLED no module loader registered` and the store code runs. Advanced apps may instead call
`FlutterOta.initialize(moduleLoader: flutterOtaLoadModule)` themselves.

## 4. Decision: the verifier entry point lives in the SDK

- `flutterOtaVerifierMain` is in `package:flutter_ota_system/src/bytecode/verifier_main.dart`,
  annotated `@pragma('vm:entry-point')`. `lib/src/flutter_ota.dart` imports that library, so it
  is part of every app that uses the SDK. The pragma keeps the function and its name in the AOT
  snapshot. **The app exports nothing.** (The prototype used `package:compat_host/...` and an
  `export` in `main.dart`; that is no longer needed.)
- `FlutterOtaVerifierService` runs
  `DartEntrypoint(appBundlePath, "package:flutter_ota_system/src/bytecode/verifier_main.dart", "flutterOtaVerifierMain")`
  on a new engine **without plugins**.
- No app code runs in that process, so the verifier gets the loader through a **callback handle**:
  the app computes `PluginUtilities.getCallbackHandle(loader)` and passes the number. The verifier
  resolves it with `PluginUtilities.getCallbackFromHandle`. This is why the loader must be a
  top-level function with `@pragma('vm:entry-point')`. If it cannot be resolved, the result is
  `UNAVAILABLE` and the patch is **not** activated (fail closed).
- **Confirmed on a device:** the callback-handle lookup works in the fresh `:flutter_ota_verify`
  process with the custom engine (`VERIFY_PROCESS status=OK` on an Android 13 phone).

## 5. Separate-process verification protocol

| Step | Detail |
| --- | --- |
| Request | Dart writes the module to `<filesDir>/flutter_ota/verify/candidate.bc` and calls `verifyInProcess(path, timeoutMs, loaderHandle)` on `flutter_ota/runtime`. Native refuses any path outside that directory. |
| Hand-over | Only a **read-only** file descriptor crosses to the service (`MSG_VERIFY`). The service reads at most 8 MiB. |
| Job | The Dart verifier calls `job` **once**. The service then sends `MSG_JOB_TAKEN` and returns bytes, loader handle and a random **nonce**. A second `job` call is refused, so module code cannot fetch the nonce. |
| Check | Load module, check the contract-3 entry, call every feature factory once. |
| Result | `result` must carry the nonce. The service sends `MSG_RESULT`, then kills its own process (modules cannot be unloaded). |
| Statuses | `OK`; `REJECTED` (clean error, e.g. VM bytecode verifier); `CRASHED` (died after job taken); `UNAVAILABLE` (died before job taken, no loader, could not bind); `TIMEOUT` (default 30 s, process killed). |
| Outcome | `OK` -> stored as pending. `UNAVAILABLE` -> not activated, not blacklisted. Everything else -> **blacklisted**, never activated (as in Phase 3C). |

The service is declared with `android:process=":flutter_ota_verify"`, `android:exported="false"`
and **without** `android:isolatedProcess` (Phase 3C proved Flutter cannot start there in release).

## 6. Crash state machine (ported from Phase 3C)

States, exit table and thresholds (`maxFailures = 2`, `maxUnconfirmedStarts = 3`) are unchanged
from the Phase 3C prototype. Crashes, ANRs and crash signals count as failures; force-stops,
low-memory kills and normal exits do not; an unknown exit counts only for an unconfirmed start.

Changes compared with the prototype:

- Storage is `<filesDir>/flutter_ota/` (`state.json`, `active.otp`, `previous.otp`,
  `pending.otp`, `attempt.json`, `session.json`, `device.json`, `verify/`, `tmp/`). All JSON
  writes are atomic (temp file, flush, rename).
- **Activation at the next start.** A verified patch is written as `pending.otp` with its SHA-256.
  At the next start, after the previous session is attributed, it is checked again (as a new
  patch, so replays fail) and activated through a **journal** (`activation` in `state.json`).
  If the process dies during the renames, the next start finishes the activation.
- A new **store release** (different `release_id`) removes the old patches and resets the
  sequence. A **corrupted** state file keeps the files; the active patch must re-verify.
- Before confirmation, an uncaught error after a patched feature was used counts as a failure
  and switches all features to the store code for the rest of the session (`LIVE_FALLBACK`).
  Existing `FlutterError.onError` / `PlatformDispatcher.onError` handlers are kept and called.
- **No test hooks** in production code. Unit tests use `FlutterOta.debugOverrides`, which is
  ignored in release builds (`kReleaseMode`).

## 7. Update check

- `POST /v1/devices/register` with `application_id` (never the slug).
- `GET /v1/updates/check` with `supported_formats=dbc-v1`, `release_version` from the config or
  `versionName+versionCode`, `current_patch_number` (server number of the active patch) and
  `failed_patch_ids` (server ids of blacklisted patches).
- The response must name this app and this `release_id`.
- `revocations`: verified with the compiled-in **root** keys only; applied only if its sequence is
  higher than the stored one. A revoked active patch fails re-verification at the next start.
- `rolled_back_patch_numbers` / `revoked_patch_numbers`: the active patch is rolled back for the
  next start; pending and previous patches with those numbers are dropped.
- Offer checks: valid ids, arch, not blacklisted/revoked, sequence newer, exact size, container
  SHA-256, full `verifyPatch` (certificates are **required**; directly trusted keys are never
  accepted), manifest `patch_id`/`sequence` equal to the offer, then the separate process.
- Events (`/v1/events/batch`, server patch ids): `patch_downloaded`, `patch_staged`,
  `patch_boot_succeeded`, `patch_boot_failed`, `patch_auto_rollback`.
- Transport: `https://` only in release builds, except plain `http://` to loopback hosts
  (`127.0.0.1`, `localhost`, `[::1]`) for local tests through `adb reverse`. LAN hosts and the
  emulator address are refused. Redirects are checked hop by hop and never downgraded from
  https. `OtaClient` keeps its https-only rule. Patches stay protected by their signatures.

## 9. Open issues

- Crash-recovery paths with the production SDK on a device (deferred to the final testing phase).
- Optional config fields read by the SDK but not yet set by the CLI: `required_approvals`,
  `host_owned_packages`.
- The SDK's `pubspec.yaml` still allows Flutter `>=3.44.9` for the classic API. The bytecode
  runtime itself needs a pinned toolchain (Flutter 3.47.9 or 3.50.0). The code was not compiled with
  3.44.9 here.
- `Es256Verifier` (ported unchanged) does not check that a public key lies on the curve. Root keys
  come from the build config, so this is not exploitable by a patch, but the config parser could
  check it.
