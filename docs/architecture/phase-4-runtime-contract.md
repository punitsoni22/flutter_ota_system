# Phase 4 runtime contract (CLI ↔ SDK ↔ patch module)

Status: binding contract for Phase 4 milestones 4C–4F. Experimental alpha, Android arm64 only.

## 1. Build-time configuration (CLI → app)

`flutter_ota.yaml` contains only `app_id`.

Everything else is injected by the CLI at build time as **one** dart-define:

```text
--dart-define=FLUTTER_OTA_CONFIG=<base64url(canonical JSON)>
```

The JSON looks like this (canonical: sorted keys, compact, no floats):

```json
{
  "format": 1,
  "app_id": "<server application UUID>",
  "server_url": "https://ota.example.invalid",
  "release_id": "<backend release UUID, chosen by the CLI before the build>",
  "environment": "production",
  "root_keys": {"<key_id>": "<base64 uncompressed P-256 point>"},
  "toolchain_id": "<sha256 toolchain id>",
  "runtime": {"abi": "android-arm64", "dart": "3.13.7", "engine": "89c39edf", "flutter": "3.47.9", "runtime_id": "..."},
  "interface_sha256": "<sha256 of dynamic_interface.yaml>",
  "host_packages": ["..."],
  "entry_contract": 3
}
```

Rules:
- No private key, admin key or secret is ever part of this config.
- The CLI keeps the build arguments in `.flutter_ota/release.json`, so later builds are reproducible.
- `FlutterOta.initialize()` reads `const String.fromEnvironment('FLUTTER_OTA_CONFIG')`.
  - If the value is empty (for example, a plain `flutter run` in debug), OTA is **disabled**: the app runs its AOT or JIT code, and a log line says why. There is no crash.

## 2. App integration (developer writes this once)

```dart
Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();
  await FlutterOta.initialize();
  runApp(const MyApp());
}
```

`initialize()` does the following:

1. **Never throws.** On any internal error it logs, and the store code runs.
2. Does **no network request on the start-up path**:
   - it verifies the stored active patch (Phase 3C pipeline);
   - it loads the patch, applies the features and returns;
   - the update check runs in the background after the first frame.
3. Confirms the start (crash state machine) after the first frame plus a stable period.

## 3. Feature slots

Patched code is reached only through features.

**Rule:** a patch contains *renamed copies* of the feature packages. So a feature's own classes become **different types** inside a patch.

The host must therefore call each feature through a **host-owned contract type**: one that is part of the store build and is never copied or renamed. There are two allowed forms:

1. **Zero-boilerplate default.**
   - The SDK provides `abstract class OtaFeature { Widget build(BuildContext context, [Object? arguments]); }` (exported by `flutter_ota_system`).
   - A feature package's entry class (convention: `<PascalName>Feature` in `lib/<package>.dart`) extends or implements `OtaFeature`.
2. **Richer API.** The entry class implements an abstract class declared in a **shared (host-owned) package**, for example `core`. Use this when a feature must expose more than a widget.

The generated registry uses the **contract type**, never the feature's own class:

```dart
// generated by flutter_ota (4F) in the app: lib/flutter_ota_features.g.dart
import 'package:flutter_ota_system/flutter_ota_system.dart';
import 'package:products/products.dart' as feature_products; // prefix feature_<package>: never clashes with a getter
abstract final class OtaFeatures {
  static OtaFeature get products =>
      FlutterOta.feature<OtaFeature>('products', () => feature_products.ProductsFeature());
}
```

**How `FlutterOta.feature<T>(name, aotFactory)` behaves:**
- It returns the patch's factory result when the active patch provides `name` and the result `is T`. `T` is a host-owned type.
- Otherwise it returns `aotFactory()`.
- A wrong type is ignored and logged. It never crashes.

**How the generator picks the contract type:**
- It uses the entry class's nearest supertype from the SDK or from a shared package.
- If the entry class has no host-owned supertype, the generator refuses with a clear message.

**What lives where:**
- Feature-internal models, repositories, widgets and generated freezed or JSON code live in the feature package. They are copied and renamed into the patch together, so they stay consistent with each other.
- Shared models used by several features are host-owned and cannot change in a patch.

## 4. Patch module entry (generated by the CLI in the module)

```dart
@pragma('dyn-module:entry-point')
Object? otaPatchEntry() => <String, Object?>{
  'contract': 3,
  'features': <String, Object? Function()>{
    'products': () => ProductsFeature(), // renamed copy
  },
  'assets': <String, Uint8List>{}, // optional
};
```

Phase 2 and 3 modules use contract 2 (direct slot objects). Contract 3 maps names to factories.

## 5. Patch artifact

- **Container:** `OTAPRT02`, signed locally by the developer's certified key.
- **Format name:** `dbc-v1` (see `phase-4-backend-protocol.md`).
- **Manifest fields** (as in `patch_security`):
  - `entry_contract: 3`;
  - `toolchain` = the toolchain record;
  - `host_interface.sha256` = `interface_sha256`;
  - `release_id` = the backend release UUID;
  - `baseline_libapp_sha256` = the SHA-256 of the store build's `libapp.so` (arm64).

## 6. Device storage and verification

- Private app storage: `<filesDir>/flutter_ota/`.
- Verification of a **new** patch runs in a separate verifier process (same UID, Phase 3C) before activation. The in-VM bytecode verifier is part of the custom engine.
- The stored patch is re-verified cryptographically at every start.
- Crash attribution uses `ApplicationExitInfo` (Phase 3C state machine).
