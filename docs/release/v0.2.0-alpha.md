# Flutter OTA System v0.2.0-alpha (pre-release)

> [!WARNING]
> Flutter OTA System is an experimental, self-hosted open-source project. It is **not
> production-ready**, has **no independent security audit**, and has **no Google Play or other
> app-store approval of any kind**. You upload your own AAB and you are responsible for your store's
> policies ([Google Play policy notes](https://github.com/punitsoni22/flutter_ota_system/blob/main/docs/policy/google-play.md)).

This is the **first release of the bytecode architecture**. Your app's feature code can be patched
over the air as signed Dart bytecode, which a custom Flutter engine runs. It is an experimental
alpha: **Android arm64 apps only**, built on **Linux x64**, with **Flutter 3.47.9 / Dart 3.13.7**
and the Flutter OTA custom engine. It is published as a GitHub **pre-release**.

## What's in this release

- **Feature patches as Dart bytecode.** Code inside feature packages is compiled to bytecode and
  shipped as a patch, including code generated by `freezed` and `json_serializable`.
- **Developer-owned signing.** You keep an offline root key and a certified signer key. The server
  only verifies signatures; it never holds a key that can sign patches.
- **Self-hosted server** (FastAPI + PostgreSQL): apps, releases, channels, staged rollouts,
  rollback and revocation. There is no hosted service.
- **On-device checks** before a patch runs:
  - signature, certificate and file hashes;
  - the patch must match the exact store build and toolchain;
  - replay protection (an older patch is never accepted again);
  - an in-engine bytecode verifier;
  - a test load in a separate process;
  - automatic rollback after 2 failed starts.
- **`flutter_ota` CLI:** `init`, `config`, `doctor`, `keys init`,
  `toolchain install|list|doctor|clean`, `upgrade`, `features`, `release android`,
  `patch android`, `status`, `rollback`.
- **Automatic toolchain download.** The CLI downloads and verifies the custom toolchain. Your own
  Flutter installation is not changed.

## Install

You need Linux x64, Docker (for the server), Git, and an Android arm64 phone. Full walkthrough:
[quick start](https://github.com/punitsoni22/flutter_ota_system/blob/main/docs/quick-start.md).

**1. Packages**

```bash
flutter pub add flutter_ota_system          # in your Flutter app
dart pub global activate flutter_ota_cli    # the flutter_ota command
```

**2. Server** (local Docker stack)

```bash
git clone https://github.com/punitsoni22/flutter_ota_system.git && cd flutter_ota_system && ./flutter-ota-system.sh setup
```

**3. Your app** (run inside your Flutter project)

```bash
flutter_ota init --app-id <server app UUID>
flutter_ota config set server-url <url>
export FLUTTER_OTA_ADMIN_KEY=<admin key>
flutter_ota toolchain install
flutter_ota keys init
```

Add this line at the start of `main()`:

```dart
await FlutterOta.initialize();
```

Keep only the arm64 ABI in `android/app/build.gradle.kts`:

```kotlin
ndk { abiFilters.clear(); abiFilters += "arm64-v8a" }
```

Then check, release, and patch:

```bash
flutter_ota doctor
flutter_ota release android                     # the store build (AAB) you upload yourself
flutter_ota patch android --channel staging     # a signed feature patch
```

**How the download is verified**

- The CLI checks the **ES256 signature** of `toolchain-index.json` with the public key built into
  the CLI.
- It then checks the **size and SHA-256** of every file it downloads against the signed index.
- You can check the release files by hand with `sha256sum -c SHA256SUMS`.

**Provenance.** There is **no GitHub build-provenance attestation** for these files. The custom
engine is built on the maintainer's machine, not in GitHub Actions. Authenticity comes from the
signed toolchain index. More detail:
[toolchain management](https://github.com/punitsoni22/flutter_ota_system/blob/main/docs/toolchain-management.md).

## Fixed since v0.1.0-alpha.1

- **AAB store builds work.** The overlay ships the unstripped engine, and the release check uses
  the engine's ELF build ID.
- **`release android` refuses builds with native libraries for non-arm64 ABIs.** Otherwise Google
  Play would offer the app to devices where it crashes.
- **A low-memory kill of the verifier process no longer blocklists a good patch.** The check is
  retried up to 3 times.
- **Malformed input is refused cleanly** on the device and the server: malformed certificates,
  revocation lists, and deeply nested JSON.
- **`flutter_ota rollback` text corrected.** Devices do not download older patches after a
  rollback, because of replay protection.

## Known limitations

Full list: [limitations](https://github.com/punitsoni22/flutter_ota_system/blob/main/docs/limitations.md).

- **Feature packages only.** Code outside feature packages needs a new store release.
- **Patched code is interpreted.** CPU-heavy code runs much slower than in the store build.
- **Larger store build.** Example: a 34-feature test app's `libapp.so` was 41.3 MB (6.6 MB stock),
  and its arm64 APK 54.5 MB (19.2 MB stock).
- **No going back to an older patch.** After a rollback, devices never fetch an older patch; fix
  forward with a new patch.
- **Malformed modules.** Most are contained by crashing the isolated verifier process, not
  rejected with a clean error.
- **Limited testing.** One tested phone; Linux developer machines only.
- **One Flutter version.** Flutter 3.47.9 only; 3.50 is planned.

## Upgrading from v0.1.0-alpha.1

- The original `OtaClient` runtime is unchanged and still available.
- The new bytecode runtime needs a **new store release** built with `flutter_ota release android`.
