# Flutter OTA System v0.1.0-alpha.1 (pre-release)

> [!WARNING]
> Flutter OTA System is an experimental, self-hosted open-source project. It has undergone internal
> testing on Linux and Android but has not been comprehensively validated in production. Do not
> use it for production OTA delivery without independent security, compatibility and reliability
> validation.

This is the **first public alpha** release. It is published as a GitHub **pre-release**.

## What Flutter OTA System is

Flutter OTA System is a **self-hosted** over-the-air (OTA) patch platform for Flutter apps. You run
the server on your own infrastructure and keep the signing key; **there is no hosted service**.
A store build ("release") can receive signed patches. The app checks for a patch, verifies it,
installs it on the next start, and falls back to the last good code if a patch fails to start.

## Features in this release

All of these exist in the code and are covered by tests or by the internal testing listed below.

- **Signed patches.** ES256 over a canonical message (app, release, patch number, platform, arch,
  format, hashes, size). The app verifies it with a key compiled into the app, plus SHA-256 and
  size checks.
- **Releases, patches and channels.** Patches belong to one store release; channels `dev`,
  `staging` and `production` (more through the API).
- **Rollouts.** Deterministic percentage rollouts, rollback, and permanent revoke.
- **Promotion checks on the server.** Raising a patch on `production` requires that it ran on
  another channel first and has no reported boot failures; overriding needs a logged reason.
- **Boot protection.** A patch that does not confirm a successful start is skipped on the next
  start; the app returns to its last good code by itself.
- **Control plane and data plane.** FastAPI answers update checks; patch files come from nginx or
  S3-compatible storage, addressed by their SHA-256.
- **Flutter client** `ota_client` (Dart package, not on pub.dev) and an example app.
- **Android Dart code patches (experimental).** `ota release android` / `ota patch android`
  on stock Flutter (no engine fork); refuses patches that change anything besides Dart code.
- **Config patches** (`mock-v1`): signed JSON or other files that the app reads at start.
- **`ota` CLI** and a static **admin page** at `/admin`.
- **One-command local stack** (`./flutter-ota-system.sh`): setup, start/stop, status, logs,
  update, backup/restore (verified), demo, CLI install, reset with confirmation.

## Installation

Requirements: Linux with Docker Engine and Docker Compose v2.20+, Git and curl. The app part also
needs Flutter and an Android device or emulator. Python 3.10+ is needed for the CLI.

```bash
git clone https://github.com/punitsoni22/flutter_ota_system.git
cd flutter_ota_system
./flutter-ota-system.sh setup     # .env with random local secrets, dev signing key, start, health checks
./flutter-ota-system.sh demo      # demo app + release, signed test patch, end-to-end checks
./flutter-ota-system.sh status    # URLs, health, and the public key for the example app
```

The full walkthrough, including the example app on a phone: [installation.md](../installation.md).
The local stack is for development and evaluation. A single-server setup exists in `deploy/` but
**has not been verified**.

## Testing status

| Platform | Testing status |
|---|---|
| Linux development environment | Internally tested |
| Android Flutter application | Internally tested |
| iOS | Not tested |
| macOS | Not tested |
| Windows | Not tested |

**Linux development environment.** Docker setup, persistence, backup and restore, reset and the
end-to-end demo (32 checks) were run on Linux. Backend tests (24), `ota_client` tests (20) and
static analysis pass. CI runs them on every push and pull request.

**Android.** Tested internally on a small number of devices (Android 13, arm64-v8a), over USB:

- **Config patches:** download, verification, activation after a restart, crash fallback,
  rollback, revoke, server outage.
- **Android code patches:** a store release, then a patch that ran; crash fallback, rollback,
  the store-policy gate, refusal of asset changes, and release re-registration (KI-1).

Android testing does not establish compatibility with every Android device, OS version, CPU
architecture (ABI) or Flutter version. No device matrix exists yet.

**Not tested:** iOS (needs macOS and Xcode; iOS code patches are not implemented), macOS and Windows
development machines, Android emulators with this release's scripts, the single-server `deploy/`
setup, upgrades between released versions, and production scale (no load tests).

## Security limitations

- **No independent security audit.**
- **Admin access:** one shared admin API key; no users, roles (RBAC), SSO or audit log.
- **Devices:** device registration is open, and there is no rate limiting.
- **Signing key:** stored as a PEM file or an environment variable. No KMS, HSM or Key Vault
  signer, and no key-rotation tooling. Protect and back up the key; whoever has it can ship code
  to your apps.
- **Patch URLs:** public and permanent (content-addressed). The files are signed, but anyone with
  a URL can download them.
- **Patch content:** a code patch changes what runs inside your users' apps. Your own review and
  testing of every patch is the main safeguard.

Read [security.md](../security.md) before deploying anything. Report vulnerabilities **privately**
as described in [SECURITY.md](../../SECURITY.md), never in public issues.

## Production warnings

- Do not use this release for production OTA delivery without your own security, compatibility
  and reliability validation.
- **App stores:** check your store's policy first. Android code patches replace compiled Dart code
  ([flutter-integration.md](../flutter-integration.md#store-policy)).
- **Flutter upgrades:** every Flutter upgrade needs a new store release. Code patches depend on
  Flutter's loader and were tested only with the Flutter versions the maintainers used.
- **Breaking changes:** APIs, the database schema and patch formats may change before 1.0, without
  migration paths.
- **Application ID:** the Android application ID `dev.flutterota.*` is used without confirmed
  ownership of `flutterota.dev`. Use your own application ID in your apps.
- **Scale:** there is no capacity or scale claim.
