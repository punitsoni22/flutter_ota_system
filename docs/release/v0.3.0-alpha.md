# Flutter OTA System v0.3.0-alpha (pre-release)

> [!WARNING]
> Flutter OTA System is an experimental, self-hosted open-source project. It is **not
> production-ready**, has **no independent security audit**, and has **no Google Play or other
> app-store approval of any kind**. You upload your own AAB and you are responsible for your store's
> policies ([Google Play policy notes](https://github.com/punitsoni22/flutter_ota_system/blob/main/docs/policy/google-play.md)).

This release adds **Flutter 3.50.0 / Dart 3.14.0** next to **Flutter 3.47.9 / Dart 3.13.7**. The
CLI chooses the toolchain that fits your project, and a project that moves to 3.50 can still patch
the 3.47.9 store release its users already have. It is an experimental alpha: **Android arm64 apps
only**, built on **Linux x64**. It is published as a GitHub **pre-release**.

| Package | Version |
| --- | --- |
| `flutter_ota_cli` (the `flutter_ota` command) | **0.3.0-alpha** |
| `flutter_ota_system` (the SDK in your app) | 0.2.0-alpha (unchanged, works with both Flutter versions) |

## What's new

- **Flutter 3.50.0 toolchain** (`flutter-3.50.0-ota.1`) next to `flutter-3.47.9-ota.1`. The
  bytecode verifier patch was ported to Dart 3.14. The security tests give the same results as on
  3.47.9.
- **Automatic toolchain choice.** `flutter_ota toolchain install` (in a project with no
  `flutter_ota.lock`) and `flutter_ota upgrade` choose the newest toolchain your project can build
  with. They check the `environment: sdk:` constraint in `pubspec.yaml` and the Android build tool
  minimums. They print why a newer toolchain was skipped.
- **Patching older releases after an upgrade.** `flutter_ota patch android` builds every patch with
  the toolchain its store release was built with, and installs that toolchain from the verified
  index if needed.
- **Several toolchains side by side.** Each toolchain has its own cache folder.
  `flutter_ota toolchain clean --unused` keeps the toolchains your local store releases still need.
- **Android build tool check.** Flutter 3.50 refuses to build below Gradle 9.3.1, Android Gradle
  plugin 9.1.1 and Kotlin Gradle plugin 2.4.10. `flutter_ota doctor` checks this, and
  `flutter_ota upgrade` warns before switching.
- **Raising the Android build tools no longer blocks patches** for older releases. Other native
  changes still do. This applies to releases made with CLI 0.3.0-alpha or newer.

## Install

You need Linux x64, Docker (for the server), Git, and an Android arm64 phone. Full walkthrough:
[quick start](https://github.com/punitsoni22/flutter_ota_system/blob/main/docs/quick-start.md).

```bash
flutter pub add flutter_ota_system          # in your Flutter app
dart pub global activate flutter_ota_cli    # the flutter_ota command (0.3.0-alpha)
```

Then, inside your Flutter project:

```bash
flutter_ota init --app-id <server app UUID>
flutter_ota config set server-url <url>
export FLUTTER_OTA_ADMIN_KEY=<admin key>
flutter_ota toolchain install     # chooses 3.50.0 or 3.47.9 for this project; writes flutter_ota.lock
flutter_ota keys init
flutter_ota doctor
flutter_ota release android       # the store build (AAB) you upload yourself
flutter_ota patch android --channel staging
```

To use one version explicitly: `flutter_ota toolchain install flutter-3.50.0-ota.1` (or
`flutter-3.47.9-ota.1`).

## Upgrading from v0.2.0-alpha

1. Update the CLI: `dart pub global activate flutter_ota_cli`. The SDK needs no update.
2. Existing projects keep their pinned toolchain (3.47.9). Nothing changes until you upgrade.
3. To move a project to 3.50:
   - raise the Android build tools to at least Gradle 9.3.1, AGP 9.1.1 and KGP 2.4.10;
   - run `flutter_ota upgrade`, then make a new store release with `flutter_ota release android`.
4. Patches for your existing 3.47.9 store release keep working: `patch android --release <id>` uses
   3.47.9. Build that patch from the release's code: after `flutter pub get` with the newer Flutter,
   `pubspec.lock` differs and the CLI refuses. Guide:
   [toolchain management](https://github.com/punitsoni22/flutter_ota_system/blob/main/docs/toolchain-management.md).

CLI 0.2.0-alpha.x keeps working with the v0.2.0-alpha toolchain index (3.47.9 only). The
v0.2.0-alpha release files are unchanged.

**How the download is verified**

- The CLI checks the **ES256 signature** of `toolchain-index.json` with the public key built into
  the CLI: key id `flutter-ota-toolchain-1`, public key `BIf+3nTyIc2zDfYQtoQMMFHiBNRT5Mco/+H6Q4yiI18MopOgUiJUeVuSoMrtVF+dzWjsVagbykjJioA8s9fdm6E=`
  (the same key as v0.2.0-alpha). The index has serial 2, so a CLI that has seen it refuses the
  older serial-1 index (anti-rollback).
- It then checks the **size and SHA-256** of every file it downloads against the signed index.

**Provenance.** There is **no GitHub build-provenance attestation** for these files. The custom
engines are built on the maintainer's machine, not in GitHub Actions. Authenticity comes from the
signed toolchain index.

| --- | --- |

## How 3.50 was tested

- **Security:** the reference verifier fixtures (including the B25/B27 cases) give identical
  verdicts on Dart 3.13 and 3.14. The 12-file signed malformed-patch corpus on a device gives the
  same results as 3.47.9: 1 clean rejection, 10 verifier-process aborts, 1 memory fault. Every bad
  patch was blocklisted, and the app stayed on its good patch.
- **Physical Android 13 arm64 phone:** release APK and AAB (installed with bundletool), a patch,
  rollback (the store `libapp.so` stays unchanged), and malformed patches.
- **Emulator:** the full corpus, AAB, cross-version patching (a 3.47.9 release patched from a
  project that moved to 3.50), and refused cross-version uploads.
- **Fresh install** from the signed index with a clean cache: automatic choice, both toolchains
  side by side, and an old release patched with its own toolchain.

## Known limitations

Full list: [limitations](https://github.com/punitsoni22/flutter_ota_system/blob/main/docs/limitations.md).

- **Feature packages only.** Code outside feature packages needs a new store release.
- **Patched code is interpreted.** CPU-heavy code runs much slower than in the store build.
- **A patch is tied to its store build and toolchain.** A 3.50 patch is never accepted by a 3.47.9
  store build, and the reverse.
- **Patching an older release after a Flutter upgrade** must be done from that release's code (see
  "Upgrading" above).
- **Releases made by CLI 0.2.0-alpha.2 or earlier** must also keep their Android build files
  unchanged when you patch them.
- **No going back to an older patch.** After a rollback, devices never fetch an older patch; fix
  forward with a new patch.
- **Malformed modules.** Most are contained by crashing the isolated verifier process, not
  rejected with a clean error.
- **Limited testing.** One tested phone; Linux developer machines only.
